# 视觉改版说明 v2.0

> 项目：户外装备洗护小程序「布仕曼洗护」
> 起因：甲方反馈界面「像毛坯房」——整体粗糙、完成度不足、缺乏品质感
> 范围：`miniprogram/` 微信小程序端全部 12 个页面（H5 端不在本次范围）

---

## 一、问题诊断：先说清「毛坯房」到底是什么

原版的问题不是「配色不好看」，而是四个结构性缺失。把它们拆开，才知道该修什么。

### 1. 零影像

户外装备洗护是「信任 + 材质」品类。用户要把三千块的冲锋衣交给陌生人，需要看见工坊、看见面料、看见洗前洗后。原版 12 个页面没有一张图，等同于把需求文档直接当成品交付。

### 2. 无层级

所有页面都是「同圆角、同内边距、同阴影的白卡片垂直堆叠」。没有尺度对比、没有编辑节奏、没有区块差异，眼睛找不到落点。首页从品牌区到知识列表，字号只有 22/24/26/28/30/32rpx 六个相近档位，等于没有层级。

### 3. 无设计系统

字号 28rpx 通吃、价格是纯文本、金色只出现在标签里、六个订单状态共用一种金色、圆角在 8/12/20/30rpx 之间随手取值、页面里散落着 `#B0541E`、`#8A5A1E`、`#A8834B` 三个未经管理的棕色。系统缺失，细节必然失控。

### 4. 无状态设计

加载是「加载中…」三个字，空态是「暂无订单」，没有骨架屏、没有插画、没有下一步动作、没有按压反馈。用户感知到的「粗糙」，很大一部分来自这些没被设计过的瞬间。

## 二、第一性原理：用户真正要解决的是什么

用户的问题不是「怎么洗」，而是**「我敢不敢把它交给你」**。

因此每个页面都必须在一屏内回答三件事：

| 用户的疑问 | 界面要给出的答案 |
| --- | --- |
| 你们靠谱吗 | 影像与材质、工坊信息、流程标准、保障承诺、可追溯的留档 |
| 我的东西会怎样 | 状态可视、洗前确认、洗前洗后对比、进度留痕 |
| 多少钱、多久、怎么拿回来 | 价格排版、工期、取送方式、费用明细 |

由此推导出五条约束每一个像素的原则：

| 原则 | 落点 |
| --- | --- |
| **材质优先** | 质感由面料纹理与工程线稿承担，装饰性色块不超过版面 10% |
| **秩序即专业** | 统一栅格、五级圆角、三级阴影、八级字阶，禁止随手取值 |
| **状态可视** | 六态订单各有独立色彩与语义说明，进度条可读而非装饰 |
| **触感反馈** | 全局按压态、过渡动效、骨架屏，界面「有回应」 |
| **克制用金** | 金色只做强调与细线，不做大面积底色 |

## 三、视觉方向：工坊手册（Atelier Manual）

原版的深绿 + 金棕是对的，问题在于「薄」。这次不换色，而是把颜色用出层次：

- **深林绿**作为场域色，承担深色块（主视觉、状态卡、会员卡）
- **纸感中性**作为内容底色，让信息可读、可久看
- **黄铜细线**作为签名细节：1rpx 的分割线、编号、印章

质感不靠贴图，靠三样东西：

1. **面料纹理**（`tex-bead` / `tex-stitch` / `tex-rain` / `tex-grid`）——水珠、缝线、雨痕、防撕裂格，用 CSS 渐变绘制，零资源体积，任何分辨率都锐利。
2. **工程线稿**——24 网格、1.7 描边、圆角端点的统一图标语言，来自 `tools/icons/build.js` 的 SVG 源。
3. **手册式排版**——英文小标（SERVICES / PROCESS / GUARANTEE）、编号列（01 02 03）、质检章（QC PASS）、表格化字段。

### 关于摄影素材

原计划采购实拍或生成工坊摄影。评估后放弃，原因有两条：

1. 生成图带平台水印，进交付物不合格；
2. 洗护服务的真实质感只能来自门店实拍，通用素材反而降低可信度。

因此本次改用**自绘矢量与纹理**建立质感，并在需要照片的位置预留了结构化的「影像槽位」（订单详情的洗前/洗后对照框、文章封面、分类样板卡），后续替换真实照片只需换一张图，不动版式。这是一个更可控、也更容易长期维护的选择。

## 四、设计系统（`miniprogram/app.wxss`）

### 色彩

| 组 | 令牌 | 用途 |
| --- | --- | --- |
| 品牌绿 | `--green-900 … --green-50`（9 级） | 深色场域、主按钮、状态 |
| 黄铜 | `--brass-700 … --brass-50`（7 级） | 强调、细线、印章、次卡 |
| 中性 | `--ink-900 … --ink-200`（8 级） | 文字与线 |
| 面 | `--paper` `--paper-2` `--paper-3` `--canvas` | 卡片与页面底 |
| 语义 | `--ok` `--warn` `--info` `--danger` | 状态与提示 |

### 字阶

`display 60 / h1 44 / h2 36 / h3 32 / body 28 / sm 26 / cap 24 / micro 22`（rpx）

规则：正文不小于 22rpx；18–21rpx 只用于英文小标与编号等装饰性文字；所有价格与统计数字使用 `tabular-nums`，保证纵向对齐。

### 间距 / 圆角 / 阴影

- 间距：4 / 8 / 12 / 16 / 20 / 24 / 28 / 32 / 40 / 44 / 56 / 64 rpx
- 圆角：`8 / 12 / 20 / 28 / 40 / 999` rpx 五级
- 阴影：`--sh-1`（卡片）/ `--sh-2`（浮起）/ `--sh-3`（主卡）

### 组件层

按钮（primary / brass / ghost / plain，含 sm 与 disabled）、胶囊筛选（chip）、标签（tag）、热门徽标、六态状态胶囊、质检章、单元格、键值行、骨架屏、空态（含插画槽）、吸底栏、步骤条。

## 六、对抗式审查

改版完成后，以「专门挑刺」的视角逐条验收。为了不靠肉眼，把能客观判定的部分写成了脚本：

```bash
npm run audit     # 设计与实现审查
npm run preview   # 重新渲染 12 页快照
```

`tools/preview/audit.js` 对**小程序与 H5 两端**同时生效，检查五类红线：

1. **渲染残值**：真实跑页面逻辑 + 真实 WXML，扫描产物中的 `undefined` / `NaN` / `[object Object]` / 空 `src`
2. **裸色值**：页面样式里是否绕过了设计令牌（令牌本身的透明度变体视为合规）
3. **字号下限**：小于 18rpx 为阻断，18–21rpx 列为待确认（须为装饰性文字）
4. **图片尺寸**：`<image>` 是否缺少尺寸类，避免图标按位图原始尺寸撑开
5. **对比度**：从 `app.wxss` 读取真实令牌值，校验正文/辅助/CTA 的关键组合

H5 端额外三项（这类故障在小程序上不存在，但 H5 上真发生过）：

6. **运行时异常**：逐路由加载成品，捕获 `pageerror` 与页面级横向溢出
7. **路由完整性**：`App.tsx` 里 `nav()` 出去的名字必须在视图 switch 中有分支
8. **构建可用性**：成品缺失时直接提示，避免「改了源码但没重新构建」的假象
9. **类型检查**：`tsc --noEmit`，专门挡「引用了不存在的变量」这类只在点击时才炸的问题
   （H5 里真实发生过：`ProfileView` 用了未注入的 `nav`）

### 审查发现并已修复的问题

| # | 问题 | 处理 |
| --- | --- | --- |
| 1 | 辅助文字 `#6B7772` 在画布底对比度仅 3.98:1 | 中性色阶整体加深（`--ink-500` → `#5D6964`，4.88:1） |
| 2 | 黄铜 CTA 白字对比度 2.96:1 | 按钮底色改用 `--brass-700`，6.21:1 |
| 3 | 6 处 16–17rpx 文字低于可读下限 | 统一抬到 18rpx |
| 4 | 订单卡缩略图编号恒为 01，重复无信息量 | 移除编号，只留样板色块 |
| 5 | 订单详情状态卡内「清洗中」重复出现两次 | 右侧改为「3 / 6」步骤指示 |
| 6 | 订单列表状态提示一律用黄铜色，已完成订单也刺眼 | 提示改为中性底，仅「待支付」用警示色 |
| 7 | 文章正文自带「1. 2.」与左侧编号列重复 | 渲染时自动剥离 |
| 8 | 分类卡描述高度不齐导致价格错位 | 固定两行高度 + 价格贴底 |
| 9 | 保障三栏文字贴边、字号过小 | 调整内边距与字号，精简文案 |
| 10 | 吸底栏遮挡表单最后一项 | 底部留白从 200rpx 提到 240–260rpx |

### 仍需人工确认的项

审查脚本输出的 34 项「待确认」全部是 18–20rpx 的英文小标与编号（SERVICES、BEFORE · AFTER、样板编号等），属设计上刻意的装饰性文字，不承载关键信息。这一判断已固化在脚本规则里，后续新增页面沿用同一标准。

## 七、如何验证本次改动

```bash
# 0. 生成改版前后对比（单文件 HTML，双击即可评审）
NODE_PATH=$(npm root -g) node tools/preview/report.js

# 1. 渲染 12 页真实截图（写入 previews/）
NODE_PATH=$(npm root -g) node tools/preview/snapshot.js

# 2. 跑设计与实现审查（阻断项为 0 才算通过）
NODE_PATH=$(npm root -g) node tools/preview/audit.js

# 3. 重新生成图标资产（改了 tools/icons/build.js 之后）
NODE_PATH=$(npm root -g) node tools/icons/build.js
```

改版前截图由同一套管线渲染 v1.0 源码得到（`git archive main` → 同一份 `tools/preview`），
所以前后对比是同一把尺子量出来的，不是拿旧设计稿去比新成品。

快照工具的做法值得说明：它不是另写一套 HTML，而是**直接执行 `miniprogram/` 里的页面 JS（含 mock 数据层）**，再把真实 WXML 编译成 HTML、把真实 WXSS 的 rpx 按 390px 视口换算，最后交给 Chromium 渲染。所以截图里看到的挤压、折行、错位，就是真机上会发生的问题——本次十项修复里有六项是这样发现的。

## 八、遗留与建议

1. ~~H5 端未同步~~（已完成）。`h5/` 已按同一套令牌与页面结构重做，构建链路同时修复：
   原 `src/icons.ts` 引用了仓库中不存在的 `../mp/icons`，H5 源码此前**无法构建**，
   `dist/` 是历史产物；现已改为自包含图标模块，`bun run build` 可复现。
2. **影像槽位待填**。洗前/洗后对照、文章封面、分类样板目前是纹理占位，门店实拍后替换即可，版式无需改动。
3. ~~动效可再进一步~~（已完成）。两端都加入了克制的入场动效：首屏区块依次上浮、列表项按 45ms 步进错开，
   统一 420ms / cubic-bezier(0.22, 0.61, 0.36, 1)；并适配 `prefers-reduced-motion`，系统开启「减少动态效果」时自动关闭。
   页面切换、列表增删的过渡仍未做，需要小程序的 `wx.createAnimation` 或 `page-container`。
4. **数据指标是示意值**。首页「12,400 件 / 3.5 天 / 68%」为结构占位，上线前须替换为真实经营数据，否则属于虚假宣传。
   这一条已写进 README 的「上线前必改」清单。
